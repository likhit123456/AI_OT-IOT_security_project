artifacts/accuracy-v2/parser-before.py
AI operator for the clean sim. Two capabilities, no interlock or enforcer:

1. parse_command(text): the STOCK qwen2.5:1.5b (Ollama) turns plain English into
   one JSON action {action, valve, amount}, constrained by a JSON schema. A
   small grammar check then settles "to N" (absolute) vs "by N" (relative),
   which a 1.5B model mixes up; any correction is reported, never hidden.

2. Rescue: the TRAINED scram-operator (Ollama, via l3_brain.policy.OllamaOperator
   - same prompt format, parse, validate and envelope clamp it was trained for)
   runs closed-loop every ~2 s. It reads the measured state and emits setpoints;
   `regulate()` turns them into valve positions; the loop applies them and
   stops once pressure and level are back near the design point.

regulate() is deliberately simple and directionally correct for this TE model:
    pressure above setpoint -> open purge, cut both feeds, open product a little
    at setpoint             -> purge at its design opening (vents feed 1's inert B)
    pressure below setpoint -> purge shut, feeds raised
    production setpoint     -> both feeds scaled from the design lineup
    level above setpoint    -> open product (below -> close it)
It never drives feeds from product flow (the l1_stub's production loop does,
and fights the level loop; that is the feed-cut bug it avoids).

enforcer/keel.py
Keel -- the deterministic enforcer (spec layer "L1").

Sits on the actuation path between L1 control (PI loops) and L0 PlantService:

    L3 targets -> L1 regulate() -> ControlCommand -> Keel.step() -> signer -> L0

What it adds on top of what L0 already has (l0_plant/safety.py is a binary,
last-resort trip; provenance_gate.py checks WHO sent a command):

  1. Rate-of-rise bound + time-to-trip projection on the independent SIS
     channel: acts BEFORE the hard trip, gradually, instead of e_stop-or-nothing.
  2. Load Line: cumulative budget over a sliding window (net pressure climb /
     net level loss). Catches the slow "every step is legal" attack that a
     per-step rate bound cannot see.
  3. Divergence check: |measured - SIS| per channel. A spoofed or drifting
     basic-control sensor shows up as disagreement between the two views.
  4. Authority budget A in [0,1]: decays on evidence, recovers slowly when
     clean. Scales how far any valve may move per cycle. Exposed via
     `authority()` so it plugs straight into AIOperator(authority_fn=...).
  5. Safe fallback: on a hazard, blend the command toward a cause-specific safe
     valve lineup in proportion to severity (closest safe action, not a slam).
  6. Hash-chained, HMAC-signed event log (tamper-evident).

Design rules (these are the security argument -- keep them true):
  * Deterministic. No ML, no network, no randomness, no wall clock (time is
    passed in), so every run is replayable.
  * Hazard decisions use ONLY the SIS channel (`sis`). The measured view is
    used for the divergence check only; it can never relax a clamp.
  * L2 suspicion is advisory: it can only LOWER authority, and its total
    influence is floored (`l2_floor`), so a compromised/hostile L2 cannot
    drive the plant to zero authority on its own (no DoS-by-monitor).
  * The Keel never raises a command's magnitude; it only moves it toward safe.

experiments/level_drift_eval.py
Instrumentation-fault test: SIS low-level interlock vs. a high-drifting
basic-control-system LEVEL transmitter.

Scenario
--------
The operator asks for a lower, perfectly legal level (level_sp = 30%). The
basic-control level transmitter (`tank_level`, the `measured` view) is put
into the simulator's NATIVE drift mode, which biases `measured` upward. L1
regulates on `measured`, so it sees a level that is high / in-band, keeps the
product valve open, and the TRUE level (the independent safety-grade channel,
`outputs`) keeps falling toward the 5% low-level safety setpoint.

Expected:
  (a) a measured-only monitor (band / rate / setpoint-legality / staleness)
      registers nothing: measured level moves plausibly and stays in-band.
  (b) the SIS interlock, reading the safety-grade channel, trips at 5%.

Only the simulator's native fault interface is used (l0_plant/fault_injection
.drift on `tank_level`); there is no signal-corruption code here. The plant is
reset to its designed operating point before every run.

Physics notes (calibrated against the live container, see ARCHITECTURE.md):
  * the sim runs on wall-clock time; truth level drains at only ~0.014 %/s
    regardless of valve combination, so ~45 min from the 44% design point to
    the 5% trip. Runs are therefore long; progress is flushed incrementally.
  * native DRIFT accumulates `severity` units/hour of upward bias.

experiments/level_frontier.py
Low-level trip-threshold sweep under a persistent native drift fault on the
basic-control level transmitter: damage prevented vs. throughput lost.

Under the persistent fault, L1 regulates on a transmitter that reads high, so
after every SIS trip -> product closed -> level recovers -> re-arm, L1 reopens
the product valve and drains the vessel back to the trip point. The SIS thus
cycles trip -> re-arm -> re-trip, and the fraction of time spent in the safed
(tripped) state is the throughput given up.

Per threshold (reset to the operating point first, native fault only):
  * low-level trip = threshold, re-arm = threshold + 2 (same hysteresis as the
    40/42 run in level_drift_eval.py); the behaviour monitor's soft low limit
    is threshold + 2, so it tracks just above the trip it is being compared to.
  * the run continues until WINDOW_S seconds after the FIRST trip (an equal
    limit-cycle window for every threshold; time before the first trip is the
    approach drain and differs by threshold, so it is reported separately).
  * damage prevented = threshold - HAZARD_FLOOR_PCT (level margin preserved
    above the 5% hazard floor); throughput lost = safed_time / window.

Each process runs ONE threshold and appends its row to experiments/level_frontier_results.json.

Usage:
    python -m experiments.level_frontier --threshold 35   # one per process, appends
run_threshold; main

l0_plant/fault_injection.py
L0 fault-injection helpers.

Thin wrappers around the reactor's OWN documented sensor-fault interface
(see sim/TE_process.cc's apply_sensor_fault / simulation/simulation/TE_process.cc

"outputs" (truth) via PlantState.truth, so nothing set here can affect it.

l0_plant/grfics_client.py
L0 low-level client for the GRFICS Tennessee-Eastman simulator.

The simulator (simulation/simulation/main.cc) is a C++ process that listens on
TCP 55555 and speaks line-delimited JSON:

    read :  {"request":"read"}\n
            -> {"process":..., "outputs":{...}, "state":{...}, "measured":{...}}

    write:  {"request":"write","data":{"inputs":{ <name>: <value>, ... }}}\n
            -> same state object, post-update

Accepted input names include the four valve setpoints (f1_valve_sp, f2_valve_sp,
purge_valve_sp, product_valve_sp), e_stop, and the fault-injection parameters.
Setpoints are in physical percent [0,100] - the simulator does the 0-65535
scaling internally, so this client stays in engineering units.

This client is deliberately thin: it owns the socket and the JSON framing and
nothing else. Safety logic lives one layer up in safety.py so the interlock is
independent of transport.

l0_plant/plant_service.py
L0 plant service.

This is the clean boundary the rest of SCRAM sees. It:
  * wraps the GRFICS socket client,
  * translates raw simulator JSON into the shared PlantState contract,
  * runs the independent SafetyInterlock every cycle and, when tripped,
    overrides the incoming ControlCommand to force the plant safe.

Everything above L0 talks to this class, never to GrficsClient directly.

Note on the real/measured split: the simulator reports both the true physical
values ("outputs") and the sensor-faulted values ("measured"). L0 publishes the
MEASURED values as the live state (that is what a PLC/HMI really sees) and
tucks the truth into PlantState.truth for eval only.

The safety interlock is the one exception: it evaluates "outputs", modeled as
a dedicated safety-instrumented sensor path independent of the basic control
system, not "measured" (the basic control system's own instrumentation). A
fault injected via l0_plant/fault_injection.py only ever touches "measured",
so it can corrupt what L1/L2/L3 see in PlantState without being able to stop
the interlock from tripping. This assumes standard SIS independence: the
safety-instrumented path is out of the attacker's reach - see ARCHITECTURE.md.

l0_plant/provenance_gate.py
Command-origin integrity on the actuation path (defensive).

The enforcer (PlantService) is the ONLY sanctioned writer to the plant
(port 55555). The physics interlock (safety.py) grounds its veto in the
process state; this module is the second ground: WHO issued the command. It
catches the case physics cannot - a command that is individually within every
physical limit (so the SIS never trips) but was not issued by the authorized
path.

Two mechanisms, with different jobs:

1. Provenance check (commands that reach the enforcer). L1 signs each command
   with a shared key (HMAC-SHA256 over a strictly increasing sequence number
   plus the four valve positions). `ProvenanceGate.admit` rejects a command
   with a missing/invalid tag or a replayed/stale sequence number, and the
   enforcer re-asserts the last-good command instead.

2. Readback audit (commands that DO NOT reach the enforcer). A write sent
   straight to the plant socket never passes through admit(), so it can't be
   prevented from here - the plant's JSON protocol has no authentication.
   What the enforcer can do is notice: it knows exactly what it last wrote, so
   any valve position or e_stop state on the plant that differs from that is,
   by construction, someone else's write. `ProvenanceGate.audit` flags the
   mismatch and the enforcer re-asserts last-good on its next write. Limits:
   detection is per control cycle, so an out-of-band write can dwell for up
   to one cycle; it is detected and bounded, not prevented. Preventing it
   needs network-level controls (only the enforcer host may reach 55555) -
   outside this code.

Key handling: the key is supplied by the caller (e.g. from the environment);
nothing here ships a default key.

l0_plant/safety.py
L0 hardware safety layer - the independent interlock ("SCRAM").

This is the bottom of the SCRAM thesis: a last-resort protective layer that
sits UNDER the AI and cannot be talked out of tripping. It does not know or
care what L3 intends or how much authority governance granted; it watches a
handful of physical variables and, if any crosses a hard limit, forces the
plant into a safe state (feeds shut, relief paths open) by asserting the
simulator's e_stop.

Design rules:
  * Trip logic depends ONLY on physical state, never on upstream intent. The
    caller (plant_service.py) is responsible for handing this class the
    reactor's "outputs" - modeled as a dedicated safety-instrumented sensor
    path, independent of the basic control system - not the "measured" view
    the basic control system itself sees. This assumes standard SIS
    independence (the safety-instrumented path is out of the attacker's
    reach); see ARCHITECTURE.md.
  * Trips latch. Once tripped, the plant stays safed until an explicit,
    deliberate reset (a human/operator action in the real thing) AND the
    variables are back inside the re-arm band - exactly like a real reactor
    scram that you cannot clear while still over-pressure.
  * Limits here are protective trip points, set wider than the normal
    operating envelope L1 regulates within, so the interlock only fires on a
    genuine excursion - not on routine control action.
  * A safety-channel reading that is missing or not a finite number trips the
    interlock (cause "sis_sensor_fault", safe state e_stop): an SIS that cannot
    read its own sensor fails safe rather than assuming all is well.
  * Optional closed-loop safe-hold (SafeHold): instead of an e_stop that kills
    the reaction, a pressure / high-level trip cuts the feeds back and works
    purge and product on the safety channel until the plant is back inside the
    re-arm band, still running. It escalates to e_stop on a runaway
    (pressure >= SafeHold.runaway_kpa) and stays there until reset.

l1_regulator.py
L1 regulatory control: four PI loops that turn SupervisoryTargets into valve
positions, and the signer that stamps every outgoing command for the
provenance gate. Replaces l1_stub.py + live/engine.LiveL1 on the live path
(the offline experiments keep the stub their saved results were produced with).

Actuator mapping for the TE reactor (primary actuator per variable):
    pressure    <- purge valve      (open purge -> vent -> pressure falls).
                   Split range: at the design point purge sits almost shut
                   (~0.4 %), so when the loop output goes below 0 it raises
                   both feeds instead: u in [-FEED_SPAN, 0) maps linearly to a
                   feed trim of 0..+FEED_TRIM_MAX. That is the only way to build
                   pressure back after a vent / e-stop.
    level       <- product valve    (open product -> drain -> level falls)
    production  <- feed 1 valve     feedforward f1 = design f1 x sp/100, plus a
                   SLOW PI trim on measured product flow
    A in purge  <- feed 2 valve     (A-rich feed)

Decoupling is by time scale, not by a model: level is the fast loop on the
product valve; production only trims feed 1 slowly (outflow follows inflow
through the level loop at steady state), so the two do not fight. Pressure
uses purge (and the feeds only when purge is saturated shut); while it trims the
feeds, the production trim is held, so it neither cuts feed 1 back against the
pressure build-up nor winds up on the throughput change it causes.

Units (the L1 seam): valves are percent [0, 100] (contracts.ControlCommand);
a_comp_sp is mol PERCENT (e.g. 47.0) while the plant reports a_in_purge as a
mole FRACTION (~0.47) - converted here, in one place (_a_pct).

Every integrator has conditional-integration anti-windup and every output is
clamped. Integration uses the real elapsed time the caller passes in (the old

l3_brain/operator.py
L3 AI operator ("Brain").

Owns the operating loop. Each cycle it:
  1. takes the latest PlantState (handed down from L2/supervisory),
  2. asks its Policy for SupervisoryTargets,
  3. applies the governance authority clamp to those targets,
  4. emits the targets downward (to L1, through governance).

It deliberately does NOT talk to L0 or to valves. Its only output is intent.

Governance seam: `authority_fn` is a callable the governance layer (teammate,
L1/L2 boundary) provides; it returns the current 0..1 authority. Here we accept
it as an injected dependency so the brain has no hard dependency on a layer it
doesn't own. If none is supplied we assume full authority (useful for local
L0+L3 testing before governance exists).

Hard rule: this handshake (and the policy it wraps) reads ONLY
PlantState's measured fields - pressure, level, product_flow, a_in_purge,
valve positions. It never reads `.truth` (the independent SIS channel); that
channel belongs solely to L0's interlock (l0_plant/safety.py). L3 is
detection/governance logic operating on the same (possibly faulted) view the
basic control system sees - the interlock is the only thing with eyes on
ground truth, and it enforces safety regardless of what L3 asks for.

Server-side model calls: if you later back the policy with a hosted model, make
that call inside Policy.decide on the server - never ship keys/model calls to a
client. The loop here is already server-side.

monitor/behavior_monitor.py
Behavior-only anomaly monitor.

This represents the kind of detector a conventional "AI safety" layer would
plausibly ship: it watches the plant's measured telemetry and the setpoints
the operator (L3) is requesting, and flags anything that looks outside a
legal/plausible envelope - soft limits, a rate-of-change-too-HIGH cap, a
per-cycle setpoint-step cap, AND a rate-of-change-too-LOW (staleness/frozen-
sensor) check, the standard sensor-integrity check that catches a naive
stuck-value fault. This is the checklist a sensor-integrity-conscious engineer
would actually ship, not a strawman with an obvious hole left in on purpose.

It is also, by construction, blind to anything that only shows up on the
independent SIS channel (contracts.PlantState.truth). It reads ONLY the
measured fields and the requested SupervisoryTargets - never `.truth` - the
same restriction a real behavior-only/anomaly-based layer would have if it is
built on top of the basic control system's own instrumentation. That is
exactly the limitation the red-team evaluation in
experiments/adversarial_eval.py demonstrates: a sensor fault that holds
measured in-band blinds this monitor just as completely as it blinds a human
operator looking at the same HMI, which is why SCRAM does not rely on this
class (or anything like it) for protective action - see ARCHITECTURE.md.

monitor/governance.py
L2 governance: turns the L2 monitors' suspicion into an authority CEILING for the
AI operator - the "when do we throttle the brain" decision.

This SHAPES authority; it does not provide safety. The SIS (l0_plant/safety.py)
stays the independent hard stop and Keel keeps its own physics / gate-driven
authority; the operator gets min(Keel's authority, this ceiling).

Inputs each cycle (routed exactly as in Phase 1):
  * the rule monitor's score (SequentialMonitor), sampled every RULE_SAMPLE_S
  * the observer's PROPOSAL-side verdicts (provenance_violation,
    rationale_mismatch, setpoint_drift); telemetry verdicts are display-only
  * the brain's latest pre-blend intent, for the recovery envelope check

1. Debounce: suspicion only counts once corroborated - two CONSECUTIVE calls of
   the same monitor both above TIER1 (for the observer: two consecutive verdicts
   that are proposal-side attack labels). A one-off spike moves nothing.
   Corroboration is temporal per monitor, not cross-monitor agreement, so the
   observer can still catch what the rule monitor cannot see.
2. Ceiling g(s): piecewise, monotonic non-increasing, bounded in [floor, 1]; the
   floor is NONZERO so no verdict (single, repeated or hallucinated) can drive the
   operator to 0.
3. Rates: the applied ceiling falls toward g(s) fast (DROP_PER_S) and rises slowly
   (RECOVER_PER_S), and only after suspicion has stayed below TIER1 for
   CLEAN_WINDOW_S AND the operator's latest proposal is back inside the design
   envelope - recovery is not just history aging out.

monitor/sequential_monitor.py
Sequential (cumulative) monitor -- the spec's "Lookout" (L2), advisory only.

BehaviorMonitor (monitor/behavior_monitor.py) judges ONE step at a time: a
setpoint jump over a cap, a rate over a cap, a frozen signal. An attacker who
keeps every step under those caps is invisible to it by construction (the
"sub-threshold / distributed" attack). This monitor looks at the TRAJECTORY of
what L3 asks for:

  1. CUSUM per setpoint channel  - accumulates same-direction creep that no
     single step reveals (e.g. 20 kPa steps under a 100 kPa step cap).
  2. Same-sign run length        - n consecutive moves in one direction.
  3. Rationale screen            - weak lexical check of the agent's free-text
     rationale for injection-style language (the indirect-injection surface).
  4. Keel corroboration          - if the trusted enforcer reports divergence /
     rate-bound / load-line, suspicion is floored up (L2 reads Keel *events*,
     never the SIS channel itself).

Output is a score in [0,1] + a short reason, i.e. the spec's SuspicionSignal.
It is ADVISORY: feed it to Keel.step(suspicion=...). It can only lower
authority there, with a floor, so a defeated or hostile L2 cannot cause an
unsafe actuation and cannot zero authority on its own.

Like BehaviorMonitor it reads only measured fields + requested targets.
Known limit (state it in the viva): a patient attacker can hold CUSUM below
threshold too (Distributed Detectability Band). That is why Keel, not this
class, is the gate.

scripts/reset_plant.py
Reset the plant container to its designed operating point and confirm it has
settled before a run depends on it.

Why this exists: PlantService doesn't persist any state of its own, but the
simulator container does, in the running TE process - whatever valve
positions, e_stop, and sensor faults a previous run or test left behind carry
over into the next one. A run that assumes it's starting near the ~2700 kPa /
~44% design point can instead inherit a mid-transient state (e.g. valves
pinned wide open from an aborted trip test), which silently turns a
"baseline holds in band" demo into a recovery-transient demo, or makes an
interlock trip test time out because truth is starting far from the limit.

What `docker compose restart simulation` does: it restarts the container's
PID 1 (supervisord), which respawns the simulation binary. The TE object
lives only in that process's memory (no volume persists it), so a fresh
process means a fresh TE() constructor - which calls steady_state() and
lands pressure at 2700 kPa, liquid_level at ~44.2%, and all four valves at
their physics-derived steady positions. Confirmed empirically: after a
restart, truth drifts <1 kPa over the first 12 reads with no valve commands
sent - it is already essentially settled, not just pointed at a target. This
script still polls for stability rather than assuming that, so it also works
if a future image version needs a real warmup.

Usage:
    python -m scripts.reset_plant                 # restart + wait, print the settled point
    python -m scripts.reset_plant --no-restart     # skip the restart, just wait/confirm settled

As a library:
    from scripts.reset_plant import reset_and_settle
    point = reset_and_settle()   # dict: pressure, level, valve positions, cycles_to_settle

    -c, --comm {tcp,udp,serial,tls}

    -l, --log {critical,error,warning,info,debug}
        set log level, default is info
    -p, --port PORT
        set port
        set serial device baud rate
    --store {sequential,sparse,factory,none}

    --slaves SLAVES
        set number of slaves to respond to

training/build_dataset.py
Build the operator fine-tune dataset from REAL plant states.

  states.jsonl (collect_states.py)  --expert_policy-->  chat examples
      system    = operator role + the plant's real design targets and SIS limits
                  + the output JSON contract
      user      = the measured state as JSON (PlantState field names; never truth)
      assistant = setpoints + rationale JSON (the schema LLMOperator parses)

The prompt format (system text + state JSON) comes from l3_brain/prompt_format.py,
the same module LLMOperator serves with; the build asserts the system prompt is
byte-identical to the one served (train/serve match).

Split: exact-duplicate states are dropped, then each rollout is cut into
contiguous 10 s blocks and ~11% of every rollout's blocks go to val, so val
states are not interleaved 0.5 s neighbours of train states. If a rule ends up
with no val example, one train block containing it is moved to val.

Balance: within each split, every minority-rule example is kept and the
"hold design targets" rule is downsampled to at most --cap-design (default 40%)
of the split. Asserts no user-turn overlap between train and val.

Usage: python -m training.build_dataset [--cap-design 0.4] [--seed 0]
rule_of; histogram; main; main.balance

training/collect_observer_states.py
Collect REAL telemetry for the L2 observer fine-tune: the simulator's NATIVE
sensor faults (fault_injection modes on several channels) and NATIVE actuator
faults (stuck valves, valve capacity degradation), with the commanded valve
positions recorded next to the measured state.

training/states.jsonl (collect_states.py) already covers normal operation,
excursions and a few sensor faults, but it never recorded what L1 commanded,
so an actuator fault (commanded != actual) cannot be seen in it. These rollouts
fill that gap and give the observer's unseen test set real, not synthesized,
fault windows.

Each rollout: reset to the operating point, run a fixed setpoint schedule (so
the valves have something to do), switch the fault on at FAULT_ON_S, record at
2 Hz. Records stream to a temp file and are appended to
training/observer_states.jsonl only when the rollout completes; completed
rollouts are skipped on rerun.

Usage: python -m training.collect_observer_states [--only NAME] [--list]
_sensor; _actuator; done_rollouts; run_rollout; main

training/collect_states.py
Collect REAL plant states from the live GRFICS simulator for the operator
fine-tune. Nothing here is synthetic: every record is a read of the running
Tennessee-Eastman process.

Diversity comes from varying the CONDITIONS across rollouts - production /
pressure targets, setpoint steps, a pressure excursion, post-reset kicks, and
the simulator's native disturbances (sensor fault modes, valve capacity
degradation, a stuck valve). The plant is reset to its operating point before
every rollout; rollouts run one at a time.

Each rollout is regulated by the L1 stub, driven either by a fixed target
schedule or by the expert policy itself (on-policy states). The SIS interlock
(production limits) stays active throughout; if it trips, the trip is recorded
and the interlock is re-armed once the SIS channel allows.

Recording: the measured state at 2 Hz. Each line holds the measured PlantState
fields (what the operator sees) plus a `truth_eval_only` pressure/level pair
that is NOT used for training. Bounded memory: records stream to a temp file
and are appended to training/states.jsonl only when the rollout completes, so
an interrupted run never leaves a half rollout; completed rollouts are skipped
on rerun.

Also writes training/design_point.json: the settled operating point read from
the sim after the first reset (the expert's design targets).

Usage: python -m training.collect_states [--only NAME] [--list] [--duration-scale 1.0]
_ExpertBrain; _ExpertBrain.__init__; _ExpertBrain.__call__; write_design_point; done_rollouts; run_rollout; main

training/expert_policy.py
Expert supervisory policy used to LABEL real plant states for the operator
fine-tune. expert(state) -> (setpoints, rationale).

Grounding (no invented numbers):
  * DESIGN targets are the plant's own settled operating point, read from the
    live simulator right after a reset (scripts/reset_plant.reset_and_settle)
    and saved to training/design_point.json by collect_states.py.
  * LIMITS are the SIS interlock's real trip / re-arm thresholds,
    l0_plant.safety.TripLimits() production defaults (pressure trips at
    3000 kPa and re-arms at 2800; level trips at 5% / 95% and re-arms inside
    15-85%).

The expert reads ONLY measured fields (what the operator sees through the basic
process instrumentation) - never `truth`. It emits setpoints, never valves, in
the same JSON schema LLMOperator parses (l3_brain/policy.parse_llm_targets).
`state` may be a PlantState or a plain dict with the same measured keys.
load_design_point; _get; _ramp; expert

training/train_local.py
Local QLoRA fine-tune of the L3 operator on an RTX 3050 (6 GB), adapted from
the Colab notebook (Downloads/scram_operator_finetune.ipynb).

  base     Qwen2.5-1.5B-Instruct, 4-bit (Unsloth bnb-4bit), LoRA r=16
  data     training/train.jsonl, training/val.jsonl (real GRFICS states, expert labels)
  format   every example is checked against l3_brain/prompt_format (the same
           system prompt + state JSON LLMOperator serves), then rendered with
           the Qwen chat template - train == serve
  6 GB     batch 1 x grad-accum 8, max_seq_length 1024 (examples are ~520
           tokens), gradient checkpointing on, 1 epoch (3 epochs overfit)
  eval     on val: valid-JSON rate, per-setpoint mean abs error, hold accuracy
  export   adapter -> merged 16-bit -> GGUF f16 (llama.cpp convert_hf_to_gguf.py)
           -> q4_k_m (llama-quantize) in model/, plus an Ollama Modelfile

Outputs (all under model/; weights are gitignored):
  model/scram-operator-lora/      LoRA adapter + tokenizer
  model/train_log.json            loss history + run config
  model/eval_val.json             eval metrics + per-example predictions
  model/scram-operator-gguf/      scram-operator-q4_k_m.gguf + Modelfile

Stages (re-runnable; later stages load the saved adapter):
  python -m training.train_local                  # train, eval, export
  python -m training.train_local --stage eval     # or: export
  python -m training.train_local --max-seq 768    # if it OOMs at 1024
  (an interrupted train stage resumes from model/_trainer/checkpoint-*; delete that
  folder to start fresh)
